# 三国杀技能三件套生成器

把一份**中文技能说明**变成三份必须互相配对、逐字对齐的代码。

## 目标产物

| # | 产物 | 落点 | 作用 |
|---|---|---|---|
| ① | 中文技能描述 | `lang/zh_CN/Package/<LangFile>.lua` | 技能名 + 技能文本。界面显示、检索、AI 判断的唯一来源 |
| ② | C++ 技能实现 | `src/package/<pkg>.cpp`（必要时 + `.h`） | 技能逻辑；在 `loadPackage()` 里 `addSkill`；新文件登记进 `QSanguosha.pro` |
| ③ | 技能 AI | `lua/ai/<pkg>-ai.lua` | AI 何时发动、如何选目标 / 选牌 / 响应询问 |

三份产物用同一个 **技能 objectName**（小写拼音，如 `jianxiong`、`luoyi`）串联。任何一处拼错都不会报错，只会**静默失效**——技能不触发或 AI 从不使用。这是本任务最常见的失败模式，每写完一份都要回头核对拼写。

## 先选路径：C++ 三件套 vs Lua 扩展包

本仓库除 C++ 路线外，还有一条**纯 Lua 扩展包**路线，代价低得多——不写 C++、不编译、不碰 Qt：

- 中文教程：`extension-doc/1-Start.lua` ~ `18-Beta.lua`（共 18 章）
- 现成示例：`extensions/Xmode.lua`
- 写法概要：`sgs.Package(name, sgs.Package_GeneralPack)` → `sgs.General(pkg, "xxx", "wei")`
  → `sgs.CreateXxxSkill{...}` → `sgs.LoadTranslationTable{...}`（中文化）→ `general:addSkill(...)` → `return {pkg}`
- 扩展包的技能 AI 写到 `lua/ai/extension-ai.lua`（见 `extension-doc/11-Fundamentals.lua:75`）

**选择规则**：

| 情况 | 走哪条路线 |
|---|---|
| 用户没有 C++ 编译环境，只想加武将 / 技能 / 卡牌 / 文案 | Lua 扩展包 |
| 要改**已有 C++ 技能**的逻辑 | C++ 三件套 |
| 需要新技能基类、改引擎行为、动 UI 或协议 | C++ 三件套 |

下文默认 C++ 路线。走 Lua 路线时，第 3、4 步替换为上述写法，产物落在
`extensions/<name>.lua` + `lua/ai/extension-ai.lua`（无需 `addMetaObject`，也无需登记 `.pro`）。

## 四个脚本（先看这张表再动手）

| 脚本 | 作用 | 何时用 |
|---|---|---|
| `scripts/parse_lang.py` | **解析** lang 文件 / 片段 → 技能要素表（形态、基类、事件、频率、需不需要技能卡、该配哪些 AI hook） | 输入是 lang 条目时，第一步就跑它；也用于查重、摸底全项目技能 |
| `scripts/scaffold_skill.py` | 根据解析结果**生成**三件套骨架（`.h` / `.cpp` / `-ai.lua` / `.lang.lua` / `README.md`） | 需要一次性拿到结构正确、TODO 明确的骨架时 |
| `scripts/inspect_skill.py` | **自检**三处是否对齐、hook 是否齐备、有没有漏 `addMetaObject` | 每次改完技能必跑；也会指出模板注释被当成真实注册这类坑 |
| `scripts/audit_ai.py` | **全项目 AI 覆盖审计**：lang 声明的每个技能 × 其 C++ `askForXXX` 调用 → 逐项核对 Lua AI hook 是否齐备，输出缺失清单（含严重度） | 需要"把整个项目的技能 AI 补齐""找出哪些技能没有 AI"时 |

> 四个脚本都是只读输入 + 只写自己指定的输出目录，不会擅自改项目源码。

### audit_ai.py 用法（全项目补齐 AI 时）

```bash
# 人类可读报告（stdout）
python scripts/audit_ai.py --root <ROOT>
# 结构化 JSON（供后续逐项补全）
python scripts/audit_ai.py --root <ROOT> --json --out audit.json
# 只看某个 package / 某个技能
python scripts/audit_ai.py --root <ROOT> --package newsgs
python scripts/audit_ai.py --root <ROOT> --skill qiao
```

报告末尾给出五档统计：`已具备` / `致命缺失 FATAL` / `降级缺失 DEGRADED` / `规则修正技零星缺失` / `lang 有条目但 C++ 未找到实现`（后者多为卡牌名，非技能，可忽略）。

**严重度依据引擎兜底行为**：

| 级别 | 涉及 hook | 后果 |
|---|---|---|
| FATAL | `ai_skill_invoke`（非 `Frequent`） | 兜底返回 nil，**AI 永不发动**该技能 |
| FATAL | `ai_skill_choice` | 兜底优先选 `cancel`/`no` 或随机 |
| FATAL | `ai_skill_exchange` / `ai_skill_cardask` | 兜底给出错误/无意义的牌，响应失败 |
| DEGRADED | `ai_skill_discard` / `playerchosen` / `cardchosen` / `cardschosen` / `askforag` | 有通用启发式兜底，技能能用但选择不聪明 |
| UNUSABLE | 视为技 / 技能卡 | 无任何注册路径，AI 想不起来使用 |

补全时按 hook 反查 C++ 的 `askForXXX` 调用点，键名规则：

- `ai_skill_invoke` / `choice` / `playerchosen` / `discard` / `cardchosen` / `cardschosen` / `askforag` → 键 = 该次调用的 `reason`；**内部技的 reason 会经 `string.gsub(reason, "%-", "_")` 归一化**（`#mingfa-effect` 实际查表键是 `#mingfa_effect`，但 C++ 里通常直接传 `"mingfa"`）。
- `ai_skill_cardask` → 键取 **prompt 首段**（`:` 之前），而不是技能名。
- 视为技还要补 `sgs.ai_skills` 条目（`getTurnUseCard`）+ `sgs.ai_skill_use_func.<CardClassName>`，二者缺一都会被判 `UNUSABLE`。

**排序辅助方法的语义**（写补全时最易踩的坑，定义在 `lua/ai/smart-ai.lua`）：

| 调用 | 默认顺序 | 加 `true` 后 |
|---|---|---|
| `self:sortByUseValue(cards)` | **降序**（价值最高在前） | 升序 |
| `self:sortByKeepValue(cards)` | **升序**（最不值钱在前） | 降序 |
| `self:sort(players, "hp")` | 升序（血最少在前） | 降序 |

据此：**拆/偷敌方**取 `sortByUseValue` 默认（拿其最贵）；**拆/弃友方**取 `sortByKeepValue` 默认（丢其最贱）。

## 项目根定位

从当前工作目录逐级向上查找 `QSanguosha.pro`，其所在目录即 `<ROOT>`。下文所有路径均相对 `<ROOT>`。

> Windows / Git Bash 注意：脚本的 `--root` 要用 Windows 形式（`C:/Users/...` 而非 `/c/Users/...`），
> 否则路径会被解释错。脚本已加校验，会直接报错而不是把三处全报成"缺失"。

## 工作流

### 第 0 步：确认输入，选一条入口

先判断手上有什么：

**入口 A —— 只有中文技能描述（或只有武将名和技能名）**

收集齐这四项再动手，不要边猜边写：

1. **技能 objectName** —— 小写拼音，无空格连字符（`jianxiong`、`luoyi`、`quhu`）。用户只给中文描述时自行拟名，并用 `scripts/inspect_skill.py` 查重名。
2. **中文技能名与描述文本** —— 直接用于 ①。
3. **所属 package** —— 决定三个文件落在哪。对照表见 `references/skill-classes.md`。
4. **是否属于已有武将 / 新武将** —— 决定是否还要在 `loadPackage()` 里建 `General` 并 `addSkill`。

**入口 B —— 已有一段符合规范的 lang 中文条目（`["xxx"]` + `[":xxx"]`）**

这种情况**先解析再生成**，不要让模型凭空判形态：

```bash
python scripts/parse_lang.py <lang文件或片段> --skill <技能名>
```

它会输出该技能的要素表（形态 / 建议基类 / 事件 / 频率 / 是否需技能卡 / 需要的 AI hook）。
解析规则与键位语义见 `references/lang-format.md`。拿到要素表后跳到第 2 步。

若条目已在项目里（即要"补全一个只有 lang、没有 C++ / AI 的技能"），再跑一次
`python scripts/inspect_skill.py <技能名>` 确认 ②③ 确实缺失，避免重复实现。

### 第 0.5 步：用规则集校准**过程**，用项目校验**内容**

**不要跳过**，但**要先分清这一步去规则集查什么**：

| 要确定的东西 | 去哪儿查 | 说明 |
|---|---|---|
| **结算流程、时机、事件顺序、优先级** | ★ **规则集** | 这是规则集的**权威范围**，照它写 |
| **用语定义**（`可`/`须`/`需`、`▶`、`并`、`依次`…） | ★ **规则集** | 决定 `cost()`／`effect()` 切分与是否原子化 |
| **某个技能当前长什么样** | **目标项目现役代码** | 规则集只作**对照**，**不照抄** |

⚠️ **为什么不能拿规则集当技能内容的"标准答案"**：官方线上武将在持续调整，而规则集是**定格**的
（网页版 2019 后停更、印刷本冻结于 2018-12）→ **规则集里的技能描述可能已经老旧**。
技能描述**以目标项目为准**；规则集用来校准它**怎么结算、什么时机触发、按什么顺序**。

```bash
# —— 查「过程」（权威，照它写）——
$PY $LK --grep <时机/用语关键词>          # 用语定义、时机、裁定案例 → 这是主用途
$PY $LK --toc && $PY $LK --read 1917 1960 # 各类事件的结算流程
# —— 查「内容」（对照用，别照抄）——
$PY $LK --general <武将> --mode <模式>    # 该模式下的版本与技能清单（供比对，非标准答案）
$PY $LK --skill <技能名>                  # 描述（参考）+ 涉及哪些时机
$PY $LK --print <印刷本页码>              # 旁证原页（页眉带 OCR 可读性等级）
$PY $LK --diff <技能名>                   # 规则集内部两源印证情况（只在规则集内部比对）
```

**★ 来源优先级（已定裁定 2026-09-17）：两源描述冲突时默认走网页版**，印刷本只作旁证。
**但注意这是"规则集内部"的优先级** —— 遇到**规则集 vs 目标项目**的分歧时，
**以项目为准写实现**，同时列出差异告知用户。用 `--priority` 复查裁定全文。

- 若技能名在索引里查不到 → 先试 `--grep` / `--grep-print` 全文检索；
  仍查不到说明它不在规则集收录范围（项目自制 / 新卡 / 已改版）→
  **直接用项目里的现役描述**，并在交付说明里标出「规则集无此条，过程按 §术语/时机 校准」。
  ⚠️ **例外**：7 个印刷本独有技能（伪·鼓舌／决偃／存嗣／擎政／神驱／雪恨／骁战）
  已裁定**不补录**，在网页版查不到它们是正常的。
- 若查到的描述与项目/用户给的不一致 → **以项目为准写实现**，
  但**列出差异让用户裁定**（可能是"项目没跟上官方调整"，也可能是"规则集那版已过时"）。
  **不要**因为规则集写的是另一版就照规则集改代码。
- 印刷本 OCR 等级「差」（乱码率 ≥ 0.35）及以下 → **不要逐字引用**，出图核对或退回网页版。
- `--diff` 的「未印证」**不能**推出「网页版有错」—— 它只说明印刷本这一页没印证，
  同样可能只是 OCR 把正文弄坏了。裁定 1 依旧生效。
- 若 `code_sgs` 不存在 → 跳过本步，但要在交付说明里注明「未用规则集校准时机/用语」。

拿到描述后，把它的 `❶❷❸` 序号抄下来，第 2 步挂事件时要用。

### 第 0.6 步：写**国战**方向 → 读 `references/guozhan.md`

国战的内容（人数适配口径、国战卡牌、结构级差异、势力可见性）已拆成**独立 reference**：
**`references/guozhan.md`** —— 写国战技能/卡牌/bot 代码前**先读它**。

先记住三条最容易踩的：

1. ★ **bot 落地与训练一律取「项目实现口径」（用户裁定）** —— 规范值与项目说明页值只作对照与报备，
   不作为训练标签的生成依据（否则标签会与宿主系统性错位）。
   **★ 唯一例外 = A 鏖战阈值**：裁定「取人数多的」= **三方取最大**（X≤6→3、7~9→4、10,11→5、12→6）。
   本项目局制 = **线下人数，支持 2–12 人**，不吃官方线上 4~8 人的限制。
2. **与人数相关的参数只有 5 个**（鏖战触发 / 野心家阈值 / 阵法技门控 / 阵法召唤④ / 游戏结束）——
   必须**集中定义成「以 X（玩家数）为输入的函数」**，不要散落成 if。
   **★ 5 项均已裁定**（2026-09-18 结案）：A 取大 / B、D 照实现 / C 不补门控（4 人以下也保留阵法技）/ E 用 2019 版。
   ⚠️ 另外：**`X/2` 与 `X//2` 的差异要看比较符** —— `> X//2` ⟺ `> X/2`（免疫）；
   `k >= X//2` 比 `>= X/2` **宽 1**（B）；`k < X//2` 比 `< X/2` **严 1**（D）—— 不要一律当成偏差。
3. **暗置武将的势力不可见** ⇒ 势力推断必须从**可见事实**推断；
   ⚠️ **现有两侧 bot 都在偷看**（老项目读真武将名 tag、FreeKill 读 `__heg_kingdom`）
   ⇒ **势力推断必须早于参数标定**。

完整规格（含逐人数展开表 + **5 项裁定结论**）：`code_sgs/data/国战模式规格.md`，检索 `$PY $LK --guozhan [人数]`。
查卡牌两源并列版本：`$PY $LK --card <牌名>`；查产品线符号：`$PY $LK --legend`。

## 红线

- **★ 先分清「过程」和「内容」——规则集的权威范围只是过程**：

  | | 谁说了算 | 规则集的作用 |
  |---|---|---|
  | **结算流程、时机、事件顺序、用语定义、优先级** | **规则集**（官方的、稳定的） | ★ **权威依据，照它写** |
  | **某个技能当前长什么样（描述内容）** | **目标项目现役代码** | 只作**对照参考**，不照抄 |

  原因：官方线上武将在持续调整，规则集是**定格**的 →
  **规则集里的技能描述可能已经老旧**。拿它当"内容标准答案"会写出过时的技能。
  → 具体技能描述**以目标项目为准**；规则集用来校准**它怎么结算、什么时机触发、按什么顺序**。

- **技能描述与项目代码不一致时**：以**项目**为准写实现；但仍要**列出差异告知用户**
  （这可能是"项目没跟上官方调整"也可能是"规则集那版已过时"，由用户判断）。
  **不要**因为规则集写的是另一版就照规则集改代码。
- **规则集术语要"翻译"成项目词汇**，不要照搬：规则集说「使用者」`▶`「作用于」
  「最终目标列表」「区域」，项目里各有对应字段（对照 `references/ruleset-baseline.md` §10）。
  规则集的**过程模型**是权威的，**用词**不是。
- **规则版本必须对齐**：同一技能在不同产品/模式描述可能不同，国战只取 `模式 == 国战`；
  印刷本的版本信息被 OCR 丢掉了，判版本只能靠 `--legend` 的 29 个产品线符号 + 文本特征，
  **不要凭"看着像国战"就下结论**。
- **引用印刷本 OCR 前看 `OCR可疑` 字段 / 页面等级**：`OCR可疑=true` 或页面等级「差」及以下的
  条目必须回原页核对（`--print <页码>` 或 `tools/render_pages.py <页码>` 出图看）；
  `data/2019ocr_cards_verified.json` 里的 22 张是人工核对过的，可直接用。
- **规则裁定权归用户**：发现疑似规则问题（描述矛盾、时机不明）不要自行判定修复，先问。
  ⚠️ 特别地：**规则集本身也可能过时或有错**。发现规则集的时机/流程与项目现役实现冲突时，
  不要默认"项目错了"，也不要默认"规则集错了"——**列出来问用户**。
- objectName 大小写敏感，三份产物必须逐字一致。
- 无 `Q_OBJECT` 的类不要写 `signals` / `slots`。
- `#` 前缀是内部触发技标记，不要为它写 `["#xxx"]` 技能名条目（该键位在 lang 里另有含义：`["#<武将名>"]` 是武将称号）。
- 修改现有 package 前先 `git status` 确认工作区状态，避免覆盖用户未提交的改动。
- 只需生成代码、不要擅自编译；本仓库体量大，编译由用户决定。

## 规则集基线（动手前先查）

### ★ 先记住：规则集管「过程」，项目管「内容」

知识库目的是**明确官方的结算流程与处理方式**，最终要落到代码里 ——
即"按目标项目代码的结算流程和时机触发方式去实现技能"。所以：

| | 谁说了算 | 规则集的作用 |
|---|---|---|
| **结算流程、时机、事件顺序、优先级** | ★ **规则集** | **权威依据，照它写** |
| **用语定义**（`可`/`须`/`需`、`▶`、`并`、`依次`…） | ★ **规则集** | 决定 `cost()`/`effect()` 切分与原子性 |
| **某个技能当前长什么样** | **目标项目现役代码** | 只作**对照**，**不照抄** |

⚠️ **官方线上武将在持续更新调整，规则集不是实时更新的** ——
规则集里的技能描述**可能已经老旧**。**具体技能描述以新的项目为准**；
规则集用来校准它**怎么结算、什么时机触发、按什么流程走**。

遇到「规则集 vs 项目」的内容分歧 → **以项目为准写实现**，同时**列出差异让用户裁定**
（可能是项目没跟上官方调整，也可能是规则集那版已过时 —— 由用户判断）。

`<ruleset-kb>\` 是官方规则集的本地知识库，有**两套来源**：

| 来源 | 内容 | 定位 |
|---|---|---|
| **网页版**（sgsrule.cn 转换结果）| 407 篇全文 + 结构化索引 | 现行规范文本 · **规则集内部默认依据** |
| **印刷本**（《规则集 V2.2（2019版）》801 页 OCR）| 全文 + 索引 + 牌堆统计 + 产品线符号表 | 第二来源 / **旁证** |

★ **已定裁定（2026-09-17）**：两源描述冲突 → **默认走网页版**，印刷本只作旁证；
印刷本独有技能 7 个不补录；网页版未收录时印刷本升为主依据。完整裁定用 `--priority` 查。
**注意这条裁定只在规则集内部生效**，不适用于「规则集 vs 项目」的分歧。

结算流程、术语语义、时机编号**以规则集为准**；技能描述**以项目为准**。

```bash
PY=<python>
LK=<ruleset-kb>/tools/lookup_ruleset.py
# —— 查「过程」：这是规则集的主用途 ——
$PY $LK --grep <时机/用语关键词>          # ① 用语定义、时机、裁定案例
$PY $LK --read 1917 1960                 # ② 各类事件的结算流程（第三章）
$PY $LK --toc                            # ③ 目录，找流程章节
# —— 查「内容」：对照参考，不是标准答案 ——
$PY $LK --general <武将> --mode <模式>   # ④ 该模式下的版本与技能清单（供比对）
$PY $LK --skill <技能名>                 # ⑤ 描述（参考）+ 涉及哪些时机 + OCR 等级
$PY $LK --print <印刷本页码>             # ⑥ 印刷本原页（旁证；页眉带 OCR 可读性等级）
$PY $LK --legend                         # ⑦ 产品线符号表 = 判版本的唯一依据
$PY $LK --card <牌名>                    # ⑧ 卡牌；网页版没有的会自动落到印刷本
$PY $LK --diff <技能名>                  # ⑨ 规则集内部两源印证情况
$PY $LK --priority                       # ⑩ 复查来源优先级裁定全文
$PY $LK --guozhan [人数]                 # ⑪ 国战人数适配表；给人数则算出该人数各阈值
```

六条硬规则：

1. **规则集管过程，项目管内容**（见上表）。技能描述别拿规则集当标准答案。
2. **规则集术语要"翻译"成项目词汇**，不要照搬 ——
   规则集说「使用者」`▶`「作用于」「最终目标列表」「区域」，项目里各有对应字段，
   见 `references/ruleset-baseline.md` §10。过程模型是权威的，**用词不是**。
3. **版本必须对齐**：`generals.json` 按 `版本号`（⒈⒉⒊…）区分版本，`版本号 → 模式` 才决定归属；
   做国战只取 `模式 == 国战`。同一技能在不同产品描述可能不同。
4. **`❶❷❸` 是时机序号**，含义查 `data/时机表.md`（各类事件的结算流程），
   该表还标出每个时机当场能发动的技能，是校验时机切分的现成样本。
5. **写国战方向 → 读 `references/guozhan.md`**（独立 reference）。三条要点：
   ① bot 落地与训练**一律取「项目实现口径」**（用户裁定），规范值/说明页值只作对照报备；
      **★ 唯一例外 = A 鏖战阈值，裁定「三方取最大」**（5 项裁定结论见表）；
   ② **与人数相关的参数只有 5 个**，必须集中成「以 X（玩家数）为输入的函数」——
      且 `X/2` vs `X//2` 的差异**要看比较符**（`> X//2` ⟺ `> X/2` 免疫；`k >= X//2` **宽 1**；
      `k < X//2` **严 1**）；
   ③ **暗置武将的势力不可见** ⇒ 势力推断必须从可见事实推断，且**必须早于参数标定**。
   ⚠️ 【连弩】：印刷本国战【连弩】写的是「次数上限+3」，但**两侧项目实际都按「无次数限制」实现**
   （FreeKill 直接复用 `crossbow`）→ 按「内容以项目为准」**保持现状 + 报备**。
6. **规则集内部两源冲突以网页版为准**；引用印刷本文本前看 OCR 等级，
   **等级「差」（乱码率 ≥ 0.35）及以下不可逐字引用** —— 314 个技能页里有 46% 属于「差」「劣」。
   `--diff` 的「未印证」不等于「网页版有错」。

记号语义（`▶` 消耗/效果分界、`▷` 条件链、`→` 延时效果、`并` 同时执行、`依次` 逐个结算、
`可`/`须`/`需` 的语气差异、`/` 合并写法）全部以规则集为准，详见
`references/ruleset-baseline.md`。

> Windows 控制台是 GBK，**不要用 `cat`/`sed`/`grep` 打印中文**（会乱码），一律走上面的检索脚本。
