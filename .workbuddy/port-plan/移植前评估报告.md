# 移植前评估报告：QSanguosha(老) → FreeKill(新)

生成日期：2026-09-15
对象仓库：
- 老项目 `<repo>`（Qt 5.14 / C++ + Lua AI，GPLv3）
- 新项目 `C:\Users\Administrator\code\FreeKill`（Qt6 + QML + Lua，GPL-3.0，fork 自 lilystudent2016/FreeKill）

---

## 0. 一句话结论

**你要移植的不是"人机对战逻辑"，而是"技能集 + AI 策略知识"。**
而且——**FreeKill 的 AI 框架里已经内置了专门适配老项目 AI 写法的兼容层**（源码注释里直接写着"神杀智慧"）。
这不是"从零移植"，是"按它预留的接口填内容"。

同时必须接受一个现实：**FreeKill 目前只有标准版 25 个武将 / 67 个技能，老项目有 669 个技能条目。差距约 10 倍。**
所以准确的说法是：**方向对了，但这是"喂内容"的长期工程，不是"移植一个模块"的一次性任务。**

## 1. 关键事实（都已实测，非推测）

### 1.1 两边的技术栈对比

| | 老项目 | FreeKill |
|---|---|---|
| 引擎语言 | C++（技能逻辑写在 C++ 里） | **Lua**（技能逻辑写在 Lua 里） |
| 技能形态 | C++ 类（TriggerSkill / ViewAsSkill / MasochismSkill…） | Lua 表 + `addEffect` 声明式 |
| 引擎 ↔ 脚本 | SWIG 包装，Lua 调 C++ 接口 | SWIG 包装，Lua 就是引擎本体 |
| AI 框架 | `lua/ai/smart-ai.lua`（7096 行）+ 21 个 `*-ai.lua` | `lua/server/ai/smart_ai.lua`（541 行）+ 4 个框架文件 |
| AI 策略总量 | **约 37,746 行 Lua** | 约 1,916 行 Lua |
| 技能数 | **669**（lang 条目） | **67**（含卡牌技能），武将 25 个 |
| 名称完全一致 | 37 个（如 jianxiong / luoyi / fankui / guicai / tuxi…） | 同上 |
| 老项目独有 | **632 个技能条目**（含卡牌名，实际技能约 497） | — |
| 测试体系 | **无** | 有（`addTest` + FkTest，标准包 18 个技能带测试） |
| 界面 | QGraphicsView（Qt5） | QML（Qt6） |
| 许可 | 代码 GPLv3 / **素材 CC BY-NC-ND 4.0** | GPL-3.0（兼容） |

### 1.2 最重要的发现：FreeKill 已预留"神杀兼容层"

`FreeKill/lua/server/ai/smart_ai.lua:68-121` 里有一段 `qsgs_wisdom_map`，
它的注释原文是：**"神杀智慧之 sgs_ex.lua: 致敬传奇靠造表创建对象写法"**。

它把老项目的 AI 写法做了**语义映射**：

| 老项目写法（你要移植的） | FreeKill 接口 |
|---|---|
| `sgs.ai_skill_invoke.<name>` | `think_skill_invoke` |
| `sgs.ai_skill_choice.<name>` | `think_choice` |
| `sgs.ai_skill_playerchosen.<name>` | `choose_targets` |
| `sgs.ai_skill_cardchosen.<name>` | `think_card_chosen` |
| `sgs.ai_skill_discard.<name>` | `choose_cards` |
| `sgs.ai_skill_use_func.<CardClass>` | `think` |

而且 FreeKill 的 AI 是**收益论驱动的**：提供 `SmartAI:getBenefitOfEvents(fn)`（`smart_ai.lua:474`），
传入一段"模拟操作"就能得到收益值——这正是老项目 `sgs.ai_skill_invoke` 里靠经验写死的判断，
在 FreeKill 里可以**改成让框架自己算**。

`jianxiong` 的对照就是活证据：

```lua
-- 老项目 lua/ai/standard-wei-ai.lua:23（靠经验写死的启发式）
sgs.ai_skill_invoke.jianxiong = function(self, data)
  if not self:willShowForMasochism() then return false end
  if self.get_AOE_subcard then self.get_AOE_subcard = nil return true end
  return not self:needKongcheng(self.player, true)
end

-- FreeKill packages/standard/pkg/skills/jianxiong.lua:16（让框架算收益）
jianxiong:addAI{
  think_skill_invoke = function(self, ai, skill_name, prompt)
    local dmg = ai.room.logic:getCurrentEvent().data
    local card = dmg.card
    if not card or player.room:getCardArea(card) ~= Card.Processing then return false end
    local val = ai:getBenefitOfEvents(function(logic)
      logic:obtainCard(player, card, true, fk.ReasonJustMove, player, jianxiong.name)
    end)
    return val > 0
  end,
}
```

**含义**：老项目 AI 里大量的"if 血少 then 发动"这类手写启发式，到了 FreeKill 大多**不需要逐字翻译**，
用 `getBenefitOfEvents` 重写往往更短、更强。这是移植的**杠杆点**，也是最省力的部分。

### 1.3 技能的"三件套"结构变了

老项目一个技能分散在三处：
1. `src/package/*.cpp` —— C++ 技能类（逻辑）
2. `lang/zh_CN/Package/*.lua` —— 中文名 + 描述
3. `lua/ai/*-ai.lua` —— AI 策略

FreeKill 一个技能**收敛到一个文件**：`packages/<pkg>/pkg/skills/<skill>.lua`，
里面同时有 `addEffect`（逻辑）、`addAI`（AI）、`addTest`（测试），中文文案在 `packages/<pkg>/i18n/zh_CN.lua`。

**这对你极其有利**：移植的粒度从"三个文件对齐"变成"一个文件搬家 + 逐个技能带测试"。

## 2. 必须先做的第一步（不要跳）

**在写任何移植代码之前，先建"资产清单 + 覆盖矩阵"。**

理由：老项目 669 条 / FreeKill 67 条，如果不先把"哪些已有、哪些要新做、哪些两边规则不同"摊在表上，
你会在第 20 个技能时彻底失去掌控——不知道进度、不知道还剩多少、不知道哪个技能移植错了。

这张表覆盖四个维度：

| 维度 | 数据来源 | 用途 |
|---|---|---|
| 技能名（objectName） | 老 `lang/zh_CN/Package/*.lua` 的 `["x"]` | 对齐的主键（两边都用小写拼音） |
| 中文名 + 描述 | 老 lang 的 `[":x"]` / FreeKill `i18n/zh_CN.lua` | 文案可直接搬 |
| C++ 实现位置 | `src/package/*.cpp` 的类定义 | 判断技能形态（触发/视为/规则修正） |
| AI 实现位置 | `lua/ai/*-ai.lua` 的相关行 | 判断 AI 是"必须重写"还是"能自动推导" |

**分类规则（决定后续工作量）**：

| 分类 | 判据 | 处理方式 |
|---|---|---|
| A. 两边完全等价 | 名称一致 + 规则描述一致 | 直接用 FreeKill 现成实现，**零工作** |
| B. 形态相同、参数不同 | 如 mashu（距离）、rende（给牌数量） | 改 FreeKill 现成实现的参数，**小时级** |
| C. 仅老项目有，形态是标准形态 | 触发技 / 视为技 / 规则修正技 | 按 FreeKill 模板新写，**这是主战场** |
| D. 仅老项目有，形态项目特有 | 需要老项目独有的引擎能力（如"军令""势力技""君主转换"） | **先查 FreeKill 有无对应机制**，没有则阻塞（见风险 R2） |
| E. 玩法模式类 | 老项目的"国战""剑阁""化身"等模式规则 | 不属于技能移植，单独立项 |

**我可以自动生成这张表**（脚本化：解析两边的技能名、中文、AI key，输出 CSV/Markdown）。
建议第一步就做它，不用等任何决策。

## 3. 建议的执行顺序（分四个阶段）

### 阶段 0：跑通环境（1~2 天）

1. 编译 FreeKill，确认能进游戏、能开单机 AI 局。
2. 跑通它的测试：`addTest` 的机制要摸清（这是你唯一的正确性保障）。
3. **验证 R1 假设**（见风险节）：FreeKill 能不能不连服务器跑单机人机。
   —— 如果它的 AI 是服务端侧运行，单机也需要本地起 server；这个必须最先确认。

### 阶段 1：打通一个技能（3~5 天）

选 **`jianxiong`**（奸雄）做试点，理由：两边都有、形态简单（受伤害后获得牌）、有现成测试可参考。

产出四样东西：
1. 一个可运行的 FreeKill 技能文件
2. 一个 `addTest` 测试用例（**必须做，这是模板**）
3. 一份《老→新移植对照记录》——记录你遇到的每一处 API 差异
4. 一个**移植 checklist**（基于这一次经验固化下来）

**这一步的真正产出不是"奸雄能跑"，而是"移植一个技能的标准流程"。**

### 阶段 2：批量移植标准形态技能（主力工作量）

按覆盖矩阵的分类 C 推进，顺序建议：
1. **标准包**（老项目 `standard-*-generals.cpp`，约 111 个 addSkill）——两边都有参照，风险最低
2. **扩展包**（lord-ex / mol / transformation / newsgs / maneuver / momentum 等）
3. 每批 5~10 个技能，**每个都带测试**，跑全量测试后再进下一批

### 阶段 3：平台期——处理分类 D 与玩法模式

把老项目独有的引擎能力（国战势力、军令、君主转换等）逐个在 FreeKill 侧找对应机制或实现。
这一阶段最不可预测，**不建议现在做计划，先做完阶段 2 再说**。

## 4. 风险清单

| # | 风险 | 严重度 | 应对 |
|---|---|---|---|
| R1 | FreeKill 的 AI 可能依赖服务端运行，单机并非真正离线 | 高 | 阶段 0 立刻验证。若需要本地 server，评估是否可接受（打安装包时把 server 作为本地进程） |
| R2 | 老项目有 FreeKill 引擎不支持的概念（国战势力技、军令、君主转换、化身…） | 高 | 覆盖矩阵里单列出来；需要时**改 FreeKill 引擎**（Lua，门槛低于 C++，但已属"改框架"） |
| R3 | 两边技能名相同但规则版本不同（如 mashu 在老项目有 owner 后缀 `mashu_machao`） | 中 | 覆盖矩阵逐条对比中文描述，不一致的标红人工裁定 |
| R4 | AI 不只是"技能 AI"，还有通用启发式（`smart-ai.lua` 7096 行：留牌、集火、卖血、距离判断…） | 中 | 这部分**不要移植**，FreeKill 有自己的通用逻辑 + 收益论。只移植技能专属 AI |
| R5 | 素材许可（老项目 `CC BY-NC-ND 4.0` 禁演绎） | 中 | 配音/立绘属"素材"；改编后分享受限。**卡牌/技能的中文描述文本属代码/文本资产，通常随 GPL 代码分发**，但商用与改编需谨慎。建议对外发布前咨询 |
| R6 | 老项目无测试，无法验证"移植是否忠实" | 中 | 只能以中文描述 + 录像为准做人工判定；这也是为什么每个技能必须自带测试——**测试是移植的验收标准本身** |

## 5. 明确不要做的事

1. **不要移植 `lua/ai/*-ai.lua` 里的通用启发式**（`smart-ai.lua` 7096 行）。
   FreeKill 有自己的通用 AI 和收益论框架，硬搬会打架。**只搬技能专属的判断**。
2. **不要逐字翻译老项目的 C++ 技能类**。
   先读 FreeKill 里形态相同的现成技能，照着它的 Lua 写法重写，比"翻译 C++"快得多也正确得多。
3. **不要在没有覆盖矩阵的情况下批量开工**。
4. **不要动 FreeKill 的 `lua/core/`**（引擎核心）——除非阶段 3 明确判断必须改。
